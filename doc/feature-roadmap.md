# 機能追加ロードマップ

新機能を追加する前に、まずこのファイルで優先度・必要性・実装順を検討してから
設計・実装に進むための計画用ドキュメントです。`doc/video-export-spec.md` が
「実装済みの挙動を記録する」ドキュメントであるのに対し、こちらは
「これから何を・どの順番で作るか」を管理する場所です。

## 運用ルール

1. 新機能の要望が出たら、まずこのファイルに項目を追加する（実装より先に書く）。
2. 各項目には「ステータス」「優先度」「規模感」「依存関係」を記入する。
   優先度・規模感は暫定でよく、実装に着手する前にユーザーと確認・調整する。
3. 複数の項目が密接に関連する場合は、依存関係を明記し、実装順が分かるようにする。
4. 実装が完了したら、その項目を「完了」ステータスにして残す（削除しない）。
   経緯や見送った理由も含めて、後から参照できる記録として蓄積する。
5. このファイル自体は仕様書ではない。詳細設計・実装済みの正確な挙動は、
   必要に応じて `doc/` 以下に個別の仕様ドキュメントを作成して分離する
   （`video-export-spec.md` はその一例）。

**ステータス**: 未着手 / 検討中 / 設計中 / 実装中 / 完了 / 保留
**優先度**: 高 / 中 / 低（すべて暫定。実装前に要確認）
**規模感**: 小（〜数時間の作業感） / 中 / 大（既存アーキテクチャの拡張が必要）

## A. プレビューポップアップ表示

### A-1. ポップアップのデフォルト表示位置を画面左上にする

- **ステータス**: 完了
- **優先度**: 中
- **規模感**: 小
- **概要**: 歌詞プレビューのポップアップ表示（フローティングウィンドウ）を開いた際、
  デフォルトの表示位置を画面左上にする。現状のデフォルト位置は要確認。
- **依存関係**: なし。A-2と合わせて実装するのが効率的。
- **実装メモ**: `.preview-popup` のCSSデフォルトを `top:88px;right:24px` から
  `top:88px;left:24px` に変更。保存済みジオメトリが無い初回はこの値が適用される。

### A-2. ポップアップの位置・サイズを永続化する

- **ステータス**: 完了
- **優先度**: 中
- **規模感**: 小〜中
- **概要**: ユーザーがポップアップを移動・リサイズした後、その位置・サイズを
  記憶し、次回開いたときに復元する。プロジェクト単位で保存するか、
  アプリ全体で共通の設定として保存するか（ブラウザ/localStorage単位）は要検討。
- **依存関係**: A-1の後に実装すると手戻りが少ない。
- **実装メモ**: プロジェクト単位ではなく、`localStorage`（キー:
  `srt-maker-popup-geometry`）でブラウザ単位・アプリ全体共通の設定として保存
  （デスクトップアプリのウィンドウ位置記憶と同じ考え方。プロジェクトを
  切り替えるたびにポップアップが飛ぶのを避けるため）。ドラッグ終了時
  （`pointerup`/`pointercancel`）と、ネイティブCSSリサイズを`ResizeObserver`で
  検知した際に、300msデバウンスして保存。復元時は現在のウィンドウサイズに対して
  `clamp()`し、画面外にはみ出さないようにしている。Playwrightでドラッグ→
  リサイズ→リロード→再オープンの一連の流れで位置・サイズが完全に復元される
  ことを確認済み。

## B. 背景の複数トラック化・タイムライン制御・トランジション

現状は「背景は画像/動画1つだけを設定できる」という前提で実装されている
（`previewBgUrl` / `currentBgKind` / `currentBgFile` は単一の値を保持）。
このセクションの項目はすべて、その前提を「背景素材を時間軸上に複数配置できる」
という設計に拡張することが土台になる。**B-1が他のB系項目すべての前提となる。**

### B-1. 背景動画・写真を複数追加できるようにする

- **ステータス**: 完了
- **優先度**: 高（B系の他項目すべての前提）
- **規模感**: 大（既存の単一背景の状態管理・保存/読込・プロジェクト永続化を
  拡張する必要がある）
- **概要**: 背景として画像/動画を複数個登録し、タイムライン上の異なる時間帯に
  配置できるようにする。ユーザーとの事前確認で、(1) サイズモード/ズーム/位置/
  透過度/ループエフェクトは素材ごとに個別設定とする、(2) B-1の時点でC-1の
  波形タイムライン同様のドラッグ配置UIまで作る、の2点を決定してから着手。
- **依存関係**: B-2・B-3・B-4はこの機能を前提にする。
- **実装メモ**:
  - **データモデル**: `previewBgUrl`/`currentBgKind`/`currentBgFile`という
    単一の状態を、`bgAssets`配列（`{id, kind, file, start, end, settings:
    {sizeMode,zoom,posX,posY,opacity,loopEffect,loopFadeDuration}}`）に置き換え。
    `bgAssets`は`start`昇順に保たれ、区間は重ならない前提。ランタイム専用の
    `bgRuntime`（`Map<id,{url,imageEl}>`、object URL・遅延デコード画像、
    プロジェクトには保存しない）を新設。
  - **UI**: `#paramSectionBg`をフラットな共有スライダー群から、素材追加
    ツールバー＋JS生成の素材リスト（`renderBgAssetList()`、種別バッジ／
    ファイル名／開始-終了時間／展開して設定／削除）に置き換え。配置UIは
    別パネルにせず、C-1の`#waveScrollInner`内に`#bgAssetTrackRow`を
    `#waveTrackRow`と並べて追加し、ズーム・スクロール・プレイヘッドを
    構造的に共有（別パネルだと同期を手動で維持する必要が生じるため）。
    ドラッグ実装（`attachBgAssetHandleDrag`/`attachBgAssetMoveDrag`/
    `commitBgAssetTime`等）はC-1のパターン（Pointer Events +
    setPointerCapture、フル再構築とその場パッチの使い分け）を踏襲しつつ、
    C-1の関数は汎用化せず独立した関数として複製——背景素材には歌詞行には
    ない「隣接素材と重ならないようクランプする」制約があるため。
  - **重なり防止**: ドラッグ時に隣接素材の境界でハードクランプ（押し出し・
    カスケードはしない）。`bgAssetNeighbors()`で配列上の前後（=時間軸上の
    前後、`start`昇順ソートを維持しているため一致）を求め、開始/終了それぞれ
    その範囲内にのみ丸める。
  - **再生・書き出しパイプラインの一般化**: `getActiveBgAsset(t)`で
    「時刻tを含む素材」を毎フレーム判定し、アクティブ素材が変わった時だけ
    `switchActiveBgAsset()`（動画は共有`<video>`要素を張り替え、画像は
    素材idごとに`bgRuntime`へ遅延デコードしてキャッシュ）。動画のループ
    位置は「素材の`start`を基準にした相対時間」で計算するよう一般化
    （`syncBgVideoToAudio`）——素材の区間が始まった瞬間に必ずフレーム0
    から再生されるようにするため。`getBgDrawSource()`/
    `drawCanvasBackground()`はアクティブ素材の`settings`を直接読むように
    変更（既存のisNaNガードは維持）。どの素材もヒットしない区間（タイムライン
    の隙間）では`getBgDrawSource()`が`null`を返し、既存のプレースホルダー
    （放射グラデーション）にフォールバックする仕様とした。
  - **永続化・移行**: `buildProjectRecord`/`saveCurrentProject`の
    `bgImageFile`/`bgKind`を`bgAssets`配列に置き換え。`applyProjectRecord`は
    `record.bgAssets`があればそのまま復元、なければ旧形式
    （`record.bgImageFile`/`bgKind`＋`previewSettings.background`の
    サイズ/ズーム/位置等）を`start:0, end:null`（曲の最後まで）の1件の
    素材に変換して読み込む、というレガシー移行パスを実装（`initProjects()`が
    生成する旧形式レコードも同じ経路を通るため追加対応不要）。
    `duplicateCurrentProject()`は既存の`Object.assign`コピーが新しい
    `bgAssets`フィールドもそのまま安全に複製するため変更不要だった。
    `getFullPreviewSettings()`/`applyFullPreviewSettings()`の
    `background`からは素材ごとに移った7項目を削除し、全体表示トグル
    （`visible`）のみ残した。
  - **検証**: Playwrightで、画像2つを複数選択追加→リスト/タイムラインへの
    連続配置、素材ごとの異なるズーム/位置設定が再生位置に応じて正しく
    切り替わること、隙間区間でプレースホルダーに戻ること、設定変更が
    再シークなしで即座に反映されること、削除、リロード後の永続化復元、
    プロジェクト複製後の独立性、タイムライン上のドラッグ（ハンドル/
    ブロック移動の両方）が隣接素材の境界で正しくクランプされ重ならない
    こと、C-1の歌詞ブロックドラッグが新しい背景トラック行追加後も
    影響を受けないことを確認済み（コンソールエラーなし）。動画アセットの
    区間境界をまたぐ実機的な同期挙動（ffmpeg等が無い開発環境のため
    合成動画フィクスチャでの自動テストは未実施）と、実際の動画書き出し
    パイプラインでの複数素材にまたがる検証は今後の課題として残る。
  - **追加要望**: 「背景（画像/動画）に追加されている素材のサムネイルが表示されるようにする」に対応。画像は`asset.file`のobject URLをそのまま`<img>`のsrcとして使用（安価・即時）。動画は非表示の`<video>`で最初のフレームをデコードし、`loadeddata`後に96x96のオフスクリーンcanvasへ`drawImage`してJPEGのdata URLを生成（`generateBgAssetThumb()`）——ライブデコードする`<video>`を一覧の行数分常駐させるのは無駄なため、静止画1枚に変換してから破棄する方式にした。サムネイルはプロジェクト保存時のペイロードには含めず（`saveCurrentProject()`は`id/kind/file/start/end/settings`のみ保存）、リロード/プロジェクト復元のたびに`generateBgAssetThumb()`を呼び直して再生成する。

### B-2. 各背景素材の再生位置をマウス操作・数値入力で指定できるようにする

- **ステータス**: 完了（B-1実装時に前倒しで統合実装）
- **優先度**: 高
- **規模感**: 中（B-1完了後）
- **概要**: B-1で追加した各背景素材について、タイムライン上での開始時間・
  終了時間を、ドラッグなどのマウス操作と、開始/終了時間の直接数値入力の
  両方で指定できるようにする。
- **依存関係**: B-1が前提。歌詞タイムライン編集UI（C-1）とUIパターンを
  共通化できる可能性がある。
- **実装メモ**: B-1の実装時点でドラッグによる配置・リサイズ（ハンドル
  ドラッグ・ブロック全体移動）まで完了済み。
- **追加要望**: 「新規追加素材の開始位置は直前素材の終了時間に自動設定」
  （`addBgAssetFromFile()`で元から実装済み・追加対応不要）、「素材リストの
  各行に開始/終了時間の数値入力欄を追加」（歌詞タイムテーブルの
  `makeTimeInput`相当だが、値が小さいためSRT形式ではなくプレーンな秒数
  テキストで入力、`commitBgAssetTime()`を通して隣接素材とのクランプも
  共有。ドラッグと双方向に同期——`buildBgAssetTimeInputs()`/
  `refreshBgAssetRowRangeLabel()`）、「素材リストの並び順をドラッグで
  入れ替えられるようにする」に対応。並べ替えは各行の`⠿`ハンドルの
  HTML5ネイティブドラッグ＆ドロップ（`attachBgAssetRowReorderDrag()`）で、
  ドロップ先の位置に配列を並べ替えたあと、各素材の長さ（`end-start`）を
  保ったまま元の並びの先頭時刻を起点に開始/終了を再計算する
  （`reorderBgAsset()`）——時間が重ならないという制約上、単純な表示順の
  入れ替えではなく実際の時刻の再計算が必要なため。Playwrightで
  `DragEvent`＋`DataTransfer`を直接dispatchして検証し、3素材の並び替え後も
  各素材の長さが保たれたまま新しい順序で連続配置されることを確認済み
  （コンソールエラーなし）。

### B-3. 背景素材の切り替わりにトランジション（クロスフェード・ディゾルブ・フェード暗転・フェード明転）を追加する

- **ステータス**: 完了
- **優先度**: 中
- **規模感**: 大（プレビュー・書き出し両方のレンダリングパイプラインを
  「常に1素材だけ描画」から「切り替わり中は2素材を合成」に拡張する必要が
  あるため、当初の見積もりより規模が大きい）
- **概要**: ユーザー要望「各画像/動画間のつなぎにトランジションを設定
  できるようにする。適用秒数も設定」に対応。B-1時点の隣接素材（間に隙間が
  ない2つの素材）の境界に、次の4種類のいずれかのトランジション＋適用秒数を
  設定できるようにする。
  - クロスフェード: 前の素材をフェードアウトしつつ次の素材をフェードイン
  - ディゾルブ: クロスフェードに近いが、イージングを変えた緩やかな混合
  - フェード（暗転）: 一度黒にフェードしてから次の素材にフェードインで復帰
  - フェード（明転）: 一度白にフェードしてから次の素材にフェードインで復帰
  - 各素材の`settings.transitionOut = {type, duration}`として「次の素材への
    切り替え方」を保持（既存の`loopEffect`＝動画が自分の区間内でループする
    瞬間のフェードとは別物、素材と素材の境界にのみ適用される）。
- **依存関係**: B-1が前提（隣接判定に`bgAssets`の`start`/`end`を使う）。
  旧ロードマップ案ではB-3を「動画ループ時エフェクトの拡張」、B-4を
  「素材の開始/終了へのエフェクト適用」と分けていたが、実際には「素材間の
  境界に適用するトランジション」という1つの機能としてまとめて実装する方が
  自然だったため、B-3にこの内容を集約し、B-4は別項目として整理し直す
  （B-4を参照）。
- **実装メモ**:
  - **プレビュー2層構成**: 従来の背景レイヤー（`#previewBg`/`#previewBgVideo`、
    layer A＝常時「現在アクティブな素材」を表示）に加えて、`#previewBgB`/
    `#previewBgVideoB`（layer B）を新設。トランジション区間外は
    `opacity:0`で完全に無効化され、区間内だけ「次の素材」をデコードして
    表示しつつ`opacity`を進捗（`progress`、0→1）に応じてフェードインさせる。
    素材ごとのサイズ/位置設定が独立していたB-1の設計上、`--preview-bg-size`
    等の**グローバル**なCSSカスタムプロパティで2層を同時に制御することは
    できないため、`applyBgTransformFor(el, videoEl, asset)`のように対象
    要素を引数化し、各レイヤーの`background-size`/`-position`を直接
    インラインスタイルで設定する形に、既存のlayer A用コードごと汎化した
    （`applyBgTransformForAsset`/`applyBgVideoLayout`は後方互換のラッパーとして残置）。
  - **黒転/白転専用の色レイヤー**: `#previewBgFadeColor`という単色の全面
    オーバーレイを追加し、フェード暗転/明転の時だけ「区間の中間点で
    不透明度1、両端で0」という三角波（`1 - |progress*2-1|`）で明滅させる。
    実装簡略化のため、暗転/明転もlayer Bのクロスフェード（`progress`に
    比例した線形フェード）は常に併走させ、その上に色のフラッシュを重ねる
    方式にした（教科書的な「中間点で瞬間的に完全に黒→切り替え→明るくなる」
    ハードカットではない）——アクティブ素材の判定自体（`getActiveBgAsset()`）
    を区間の途中で切り替える設計にすると複雑化するため、区間の終わりで
    切り替わる既存の判定はそのまま維持し、見た目だけ「色を経由してクロス
    ディゾルブする」形に寄せた。動画がlayer Bに来る場合の実際のプリロール
    再生（区間中に次の動画を先読みしながら実際に再生する）は当初未実装
    だったが、後日の不具合修正で対応済み（下記「動画→動画のクロスフェード
    中、次の動画が静止フレームのままだった」の項を参照）。
  - **書き出し（canvas export）**: `getBgDrawSource()`を
    `getBgDrawSourceFor(asset, videoEl)`に汎化し、`drawCanvasBackground()`が
    `getBgTransitionState()`を見てtransition中はfromソース（layer A相当）を
    先に描画してからtoソース（layer B相当、`previewBgVideoB`）を
    `ctx.globalAlpha`で重ね描き、暗転/明転の場合はさらに単色矩形を同じ
    アルファ計算で重ねる——プレビューと書き出しが同一の`progress`計算
    （`bgTransitionLayerAlpha`/`bgTransitionColorAlpha`）を共有するため、
    見た目が一致する。
  - **駆動**: `getBgTransitionState(t)`が「隙間なく隣接し、かつ`transitionOut.
    type!=='none'`な境界」を毎フレーム判定。既存の背景同期用rAFループ
    （`bgVideoFadeLoop`、動画ループフェード計算と共用）から
    `applyBgTransitionFrame()`を呼ぶことで、`timeupdate`イベント（ブラウザに
    よっては間引かれる）に頼らず滑らかにアニメーションする。
  - **検証**: Playwrightで3つの画像素材を追加し、境界にクロスフェード
    （1.0秒）を設定して区間の中間点（進捗0.5）にシークしたところlayer Bの
    `opacity`が正確に`0.5`になることを確認。フェード暗転では区間の中間点で
    色レイヤーの`opacity`が`1`（両端では`0`）になることも確認。
    コンソールエラーなし。
  - **不具合修正（ユーザー報告）**: 「背景動画のつなぎでトランジションを設定していた場合、次の動画とのつながりがぎこちなく再生されてしまう」との指摘。
    - **原因**: トランジション区間中、layer B（`previewBgVideoB`）は次の動画をフレーム0で先読み・待機させていたが、実際のハンドオフ（アクティブ素材が切り替わる瞬間）が来ると、`switchActiveBgAsset()`はlayer Bの状態を一切参照せず、常にlayer A（`previewBgVideo`）に対して`activateBgVideo()`（＝`src`再設定＋`.load()`のフルリロード）を呼んでいた。layer Bで既にデコード済み・frame0で待機していた**同じ動画**を、ハンドオフの瞬間にもう一度ゼロから読み込み直していたため、その瞬間だけ再バッファリングによる一瞬のフリーズ/巻き戻りが発生し「ぎこちない」再生になっていた。
    - **対策**: 「layer A＝常にアクティブ」「layer B＝常にトランジションプレビュー」という固定の役割分担をやめ、`primaryBg/primaryVideo`・`secondaryBg/secondaryVideo`という**役割変数**（どちらの物理DOM要素が現在どちらの役割かを保持、`let`で再代入可能）に置き換えた。ハンドオフの瞬間、切り替わる先の素材が直前までsecondary（トランジションプレビュー）側で表示されていたものと同じであれば、`swapBgLayers()`で役割を入れ替えるだけにし、`src`の再設定や`.load()`は一切行わない——secondary側は既にフレーム0で待機済みなので、役割を入れ替えた瞬間からそのまま連続再生できる。入れ替え後、元primary（今secondary）はクリアして次のトランジションプレビュー用に再利用する。
    - `applyBgVideoLayoutFor`/`applyBgTransformFor`/`applyBgOpacityFor`/`syncBgVideoToAudio`/`getBgVideoLoopAlpha`/`getBgDrawSourceFor`など、レイヤーに依存する既存関数をすべて「固定の物理要素」ではなく「現在のprimary/secondary変数」を参照する形に汎化。書き出し（canvas export）側の`drawCanvasBackground()`も同様に対応。
    - **見つけて直した競合状態**: 素朴に「トランジション状態の更新」と「アクティブ素材の切り替え」を別々のタイミング（前者はrAFループ、後者は`audioEl`の`timeupdate`等）で走らせると、ちょうど区間が終わる瞬間に「もうトランジション中ではない」と判定されてsecondaryレイヤーの情報が先に破棄され、直後の切り替え処理が入れ替え可能なタイミングを逃してリロード処理にフォールバックしてしまう1フレームの競合があった。トランジション状態の更新とアクティブ素材の切り替えを`updateActiveBgAsset()`という1つの関数に統合し、「トランジション状態を先に反映→アクティブ素材の切り替え（入れ替え判定はここで発生）→（入れ替えが起きなかった場合のみ）トランジション状態のクリーンアップ」という順序を固定することで解消。
    - **検証**: 両方の物理`<video>`要素に`loadstart`イベントカウンターを仕込み、実尺の異なる3本のテスト動画をクロスフェードでつないで最初から最後まで連続再生。2回のハンドオフをまたいでも合計ロード回数が3回（＝動画ファイルごとに1回のみ、リロードなし）に収まること、`readyState`が再生中一度も低下しない（＝バッファリング待ちが発生しない）ことをPlaywrightで確認。クロスフェードの`opacity`が中間点で正確に0.5になることも別途再確認。コンソールエラーなし。
  - **不具合修正（ユーザー報告）**: 「背景（画像/動画）で、2回に1回の確率でトランジションが適用されない」との指摘。
    - **原因**: `getBgTransitionState()`の隣接判定が`next.start === a.end`という厳密な浮動小数点の完全一致だった。ところが素材の配置は複数の独立した経路（自動連続配置、`resequenceBgAssetsFrom`による押し出し、`reorderBgAsset`による並べ替え、ドラッグ、手動の数値入力）を経由し、それぞれが個別に`Math.round(...*1000)/1000`で丸めるため、見た目には隙間なくつながっているつもりでも実際の値が1〜数ミリ秒ずれることがあった（ドラッグはさらに粗い10ms単位に量子化される）。ずれが生じた境界だけトランジションが完全に無効化され、見た目上は「時々（体感で約半分）トランジションが効かない」という再現性の低い不具合として現れていた。Playwrightで実際に1ms（`00:00:01.999`と`00:00:02.000`）のずれを注入したところ、トランジションのopacityが全く変化しない（常に0のまま）ことを確認し、原因を実証。
    - **対策**: 新規`bgAssetsAreAdjacent(asset, next)`で、厳密一致の代わりに`Math.abs(next.start - asset.end) <= 0.02`（20ms、典型的なドラッグの量子化幅より余裕を持たせた許容誤差）による判定に変更。`getBgTransitionState()`の隣接判定と、素材設定パネルの「次の素材が隣接している場合のみ効果がある」旨のツールチップ表示判定（`hasAdjacentNext`）の両方をこの共通関数に統一し、実際にトランジションが効くかどうかとUI上の案内表示が食い違わないようにした。
    - **検証**: 上記の1msギャップ注入テストで、修正後はopacityが正しく0→1にランプすることを確認。既存のトランジション連鎖（4素材・3境界）・シームレスハンドオフ（読み込み回数・readyState）の回帰テストもすべて再実行し、影響がないことを確認。コンソールエラーなし。
  - **不具合修正（ユーザー指摘）**: 「動画→動画のクロスフェード中、次の動画が静止フレームのままフェードインしているのでは（＝時間軸上でstart/endを実際に重複させないと本物のオーバーラップ効果にならないのでは）」との指摘。
    - **切り分け**: タイムライン上の`start`/`end`自体を重複させる設計にはなっていない（`getBgTransitionState()`は隙間ゼロで隣接する境界にのみ効果を出す合成トリック）ため「区間が重複していないと適用されない」わけではないが、`activateBgLayerB()`はトランジション区間中、次の動画を`currentTime=0`に固定したまま`.play()`を呼んでおらず、実際には静止フレームがフェードインするだけだった。動画→動画の組み合わせでは、これが「期待したクロスフェード効果が得られない」の直接原因になっていた（画像がらみは元々静止画なので影響なし）。
    - **対策**: `syncBgVideoToAudio`を`syncBgVideoElementToAudio(videoEl, asset, forceRestart)`に汎化し、「その素材のフレーム0とみなす基準時刻」を`asset.start`固定ではなく`asset.start - bgAssetPreRollSec(asset)`に変更。`bgAssetPreRollSec(asset)`は「直前の隣接素材に有効な`transitionOut`が設定されている場合、その`duration`」を返す（通常は0＝従来どおり）。これにより、トランジション区間が始まった瞬間（`activateBgLayerB()`内で`loadedmetadata`後に`syncBgVideoElementToAudio(secondaryVideo, asset, true)`→再生中なら`.play()`）から次の動画が実際に再生され、境界をまたいでprimary/secondaryの役割が入れ替わった後も**同じ基準時刻**を使い続けるため、ハンドオフの瞬間に巻き戻り・ジャンプが起きない（`switchActiveBgAsset()`のスワップ経路が呼ぶ`syncBgVideoToAudio(true)`は、既にプレビュー中に到達していたのとほぼ同じ位置を再計算するだけになる）。`audioEl`の`play`/`pause`イベントハンドラも、トランジションプレビュー中のsecondaryVideoを再生/一時停止するよう対応。
    - **検証**: Playwrightで2本の動画をクロスフェード（0.6秒）でつなぎ、境界をまたいで再生。区間内で`previewBgVideoB.currentTime`が単調に増加し続ける（フリーズしていない）こと、`paused===false`であること、境界前後で`currentTime`が連続している（ジャンプしない）ことを確認。既存の回帰テスト（隣接判定の許容誤差、トランジション連鎖、シームレスハンドオフの読み込み回数・readyState）もすべて再実行し、影響がないことを確認。コンソールエラーなし。

### B-5. 背景素材リストの各行に、歌詞タイムテーブルと同じ「前後・現在位置との時間同期」コントロールを追加する

- **ステータス**: 完了
- **優先度**: 中
- **規模感**: 小
- **概要**: ユーザー要望「背景（画像/動画）の各素材行コントロールに、歌詞タイムテーブルの各歌詞行の開始/終了時間編集コントロールと同じコントロールを追加する」に対応。次の4つのボタンを、B-2で追加済みの各素材行の開始/終了時間入力欄まわりに追加した。

  - 「終了時間を次の素材の開始時間に合わせる」（⇥）
  - 「現在の再生位置を開始時間にセット」（⏱）
  - 「現在の再生位置を終了時間にセット」（⏱）
- **依存関係**: B-2（各素材行への時間数値入力欄の追加）が前提。歌詞タイムテーブル側の同等機能（`renderTable()`内の`prevSyncBtn`/`nowStartBtn`/`nowEndBtn`/`syncBtn`、`syncStartToPrevEnd()`/`syncEndToNextStart()`、`.rowbtn`スタイル）をUIパターン・実装として流用。
- **実装メモ**: `buildBgAssetTimeField(asset, field)`（`src/index.html`）内に、既存の`.time-input-wrap`（数値入力＋▲▼ステッパー）を歌詞タイムテーブルと同じ`.time-cell-row`でラップし、両脇に`.rowbtn`スタイルのボタンを追加する形にした。開始側は`⇤`（前の素材の`end`に合わせる）→`⏱`（現在の再生位置を`start`にセット）→入力欄、終了側は入力欄→`⏱`（現在の再生位置を`end`にセット）→`⇥`（次の素材の`start`に合わせる）の順で、歌詞タイムテーブルの`startRow`/`endRow`のボタン配置と対称にした。4つのボタンいずれも、既存のクランプ・保存・再描画ロジックをそのまま持つ`commit(sec)`（`buildBgAssetTimeField`内のローカル関数）経由で値をセットするため、境界値のクランプや`scheduleSaveSession()`は数値入力・▲▼ステッパーと完全に共通。隣接素材が無い/現在の再生位置が未定（音源未読込）の場合はボタンを`disabled`にする（`bgAssetNeighbors(asset)`と`audioEl.src`で判定）。

### B-6. 背景動画素材について、動画ファイル自体の再生区間（イン/アウト点）をトリミングできるようにする

- **ステータス**: 完了
- **優先度**: 中
- **規模感**: 中〜大（プレビュー・書き出し両方の動画同期ロジックに手を入れる必要があった）
- **背景**: ユーザー報告「動画素材のトリミングが正しく動作しない」の調査の結果、これに該当する機能自体が現状未実装であることが判明。ユーザーに確認したところ、期待していたのは音源のトリミング（E-1）と同種の「動画ファイル自体の再生区間を切り詰める機能」（＝タイムライン配置の`start`/`end`とは別に、動画ソースファイルのどこから再生を始めるか）だった。
- **決定事項**（ユーザーに確認済み）: スコープは開始・終了側の両方（E-1と対称）。UIは波形ビューのトリムハンドルと同様の、ドラッグ操作可能なビジュアルUIを採用。
- **旧来の挙動**: 各背景動画素材は、タイムライン上の自分の表示区間（`asset.start`〜`asset.end`）が始まった瞬間、常に動画ファイル自身のフレーム0から再生を始めていた。表示区間が動画本編より長い場合は、動画の末尾に達すると自動的にフレーム0へループしていた。
- **依存関係**: B-1（複数背景素材の基盤）が前提。E-1（音源トリミング）とは独立した別機能だが、UI設計・実装パターン（トリム範囲の保持、クランプ）を参考にした。
- **実装メモ**: `makeDefaultBgAssetSettings()`に`videoTrimStart`（秒、既定0）・`videoTrimEnd`（秒 | `null`=末尾まで）を追加。共通ヘルパー`bgAssetVideoTrimRange(asset, dur)`が、既知のメディア長`dur`に対してこれらをクランプ済みの`{start,end,span}`に解決する。
  - **再生同期**: `syncBgVideoElementToAudio()`の`target`計算を、素のフレーム0基準の剰余演算（`(audioEl.currentTime - basisStart) % dur`）から、トリム区間基準（`trim.start + ((audioEl.currentTime - basisStart) % trim.span)`）に変更。プレビュー（`primaryVideo`/`secondaryVideo`の両レイヤー、B-3のトランジションプレビュー含む）と書き出し（canvas export）が元々この同じ関数を共有していた（B-3のクロスフェード実装時に確立された設計方針）ため、この1箇所の変更だけで両方に反映される——背景の動画には音源トリム（E-1）のような「プレビューには反映しない」という区別が存在せず、プレビューに映っている`<video>`要素をそのままcanvasキャプチャして書き出す構造上、そもそも別経路を持ちようがない。
  - **ループ可視化との整合**: `bgAssetLoopBoundaries()`・`renderBgAssetLoopMarkers()`のループ境界計算を、素の`asset.mediaDuration`基準から`bgAssetVideoTrimRange(asset, asset.mediaDuration).span`基準に変更し、トリム後の短い区間で頻繁にループする場合もタイムライン上のループマーカー・オーバーレイの本数/ツールチップ文言が正しく追随するようにした。
  - **UI（初版、後に廃止）**: 当初は素材設定パネル内に`buildBgAssetVideoTrimControl(asset)`で専用のトリミングバー（0〜`mediaDuration`に対する%位置の2ハンドル）を追加し、トリム区間とタイムライン配置時間を完全に独立させ、配置時間の方が長ければトリム区間内でループするという設計にした。Playwrightで、ドラッグに応じて帯の表示・実際の`<video>`要素の`currentTime`が追随すること、ループマーカーがトリム後の区間長に追随することを確認して一度は「完了」としていた。
  - **設計のやり直し（ユーザーからの再指摘）**: 上記初版に対し「20〜30秒だけを使いたい場合、開始側を20秒地点までトリムしても、結果的に0秒地点が20秒地点に移動するだけで正しいトリミング結果にならない」との指摘を受けた。原因は認識のズレで、ユーザーが意図する「トリミング」は一般的な非破壊動画編集ツールの挙動（タイムライン上のクリップ端をつかんで引っ張ると、そのままソースのイン/アウト点が動き、かつクリップの表示時間もその分だけ短くなる。トリム区間と表示時間は常に一致し、独立したループ用の「表示時間」という概念自体が無い）であり、初版の「トリム区間とタイムライン配置時間が独立していてループする」という設計とは根本的に異なっていた。ユーザーに再確認の上、「B-2の既存のタイムラインドラッグハンドル（`attachBgAssetHandleDrag`）をそのままトリミング操作に統合する（設定パネル内の専用バーは廃止）」方針に作り直した。
  - **再実装**: `commitBgAssetTime(asset, field, sec)`（B-2のタイムライン端ドラッグ・数値入力・B-5の同期ボタンなど、`asset.start`/`asset.end`を変更するすべての経路が通る共通関数）に、動画素材の場合の連動処理を追加。`start`側なら「新しい`asset.start` − 元の`asset.start`」のデルタを`videoTrimStart`にもそのまま加算（`[0, videoTrimEnd-0.05]`にクランプ）、`end`側なら同様のデルタを`videoTrimEnd`に加算（`[videoTrimStart+0.05, mediaDuration]`にクランプ）。`asset.start`/`asset.end`側のクランプ（隣接素材との衝突防止）とはあえて完全に連動させず、それぞれ独立してクランプすることで以下の両立を実現：(1) ソース側にまだ未使用の区間がある間は、タイムライン位置とトリムイン/アウト点が1対1で連動する（＝ループなしの純粋なトリム、ユーザーの期待通り）。(2) トリムがソースの限界（0または`mediaDuration`）に達した後もタイムライン端をさらに広げる方向にドラッグし続けた場合は、トリム値はそこで頭打ちになる一方タイムライン配置はそのまま伸び続け、結果的に「トリムし切った区間を配置時間いっぱいにループさせる」という元からある挙動（B-1由来、ループマーカー表示もそのまま流用）に自然にフォールバックする——短い素材を意図的にループさせて長く見せたいという既存のユースケースを壊さずに両立。設定パネル内の専用バー（`buildBgAssetVideoTrimControl`/`refreshBgAssetVideoTrimDom`/`attachBgAssetVideoTrimDrag`と関連CSS）は削除。

### B-7. 背景素材（画像/動画）ごとに、登場（イン）・退場（アウト）のアニメーションを設定できるようにする

- **ステータス**: 完了
- **優先度**: 中
- **規模感**: 大（新規のイン/アウト演出システムに加え、B-3トランジションの重複コードを共通化するリファクタリングを伴った）
- **概要**: ユーザー要望「素材（画像/動画）のイン/アウトのアニメーションを設定できるようにする」に対応。各背景素材が自分の表示区間の開始・終了時に単体で再生する演出（種類：オフ／フェード（暗転）／フェード（明転）／ディゾルブ／ぼかし／ズーム）を追加した。
- **B-3との関係**（ユーザーに確認済み）: B-3（隣接する2素材間の切り替えトランジション）とは別軸の独立した機能として実装。隣接境界でB-3のトランジションとこのイン/アウト演出の両方が設定されていた場合は、**B-3のトランジションを優先**し、その境界ではイン/アウト演出を発動させない（ユーザーに確認の上で決定）。
- **アーキテクチャ調査結果**: 従来のB-3トランジション実装は、「タイプ名で分岐する処理」が`bgTransitionLayerAlpha()`（進捗→不透明度）と、`updateActiveBgAsset()`（プレビュー側のDOM/CSS適用）・`drawCanvasBackground()`（書き出し側のcanvas適用）の2箇所に重複した`type==='fadeBlack'||type==='fadeWhite'`判定という形で存在しており、レジストリ（タイプ名→実装のテーブル）にはなっていなかった。
- **決定事項**（ユーザーに確認済み）: イン/アウトの適用時間は素材ごとに数値入力で個別指定できるようにした。設計を詰めた結果、B-3（2レイヤーを進捗の中間点に向けてハンプ状にブレンドする）とB-7（1レイヤーが単独で現れる/消える、片側だけの単調なランプ）は数式の形が本質的に異なると判明したため、**完全に同一の関数**を両方に使う「統合」ではなく、(1) 実質的に重複していた「fadeBlack/fadeWhiteの色」だけを`BG_FX_OVERLAY_COLOR`という1つのテーブルに切り出してB-3・B-7両方から参照させ、(2) B-7自体は「タイプ名→進捗に応じた見た目パラメータを返す関数」という**同じ設計パターン**の別レジストリ（`BG_INOUT_FX_TYPES`/`bgInOutFxStyleAt()`）として新設する、という形に落ち着いた。EQビジュアライザー側は当初の想定通り対象外（形が違いすぎるため）。
- **実装メモ**:
  - `asset.settings`に`animIn`/`animOut`（各`{type, duration}`、既定`{type:'none', duration:0.6}`）を追加。
  - `bgInOutFxStyleAt(type, progress)`（`progress`: 0=効果window開始点／未確定な状態、1=通常表示に収まった状態）が`{opacity, colorOverlay, colorAlpha, blurPx, scale}`を返す。`fadeBlack`/`fadeWhite`は`BG_FX_OVERLAY_COLOR`（`{fadeBlack:'#000', fadeWhite:'#fff'}`）を参照した単調な色オーバーレイのランプ（B-3の中間点ハンプ形状とは別物）、`dissolve`は不透明度ランプ、`blur`は`ctx.filter`/CSS`filter`用のぼかし量ランプ（最大24px固定）、`zoom`は`ctx.transform`/CSS`transform:scale()`用の拡大率ランプ（最大+18%固定、イン側は縮小→等倍、アウト側は等倍→拡大で対称）。
  - `getBgInOutFxState(asset, t)`が、`asset.start`から`animIn.duration`秒間の「イン」区間、`asset.end`の`animOut.duration`秒前からの「アウト」区間を判定し、該当すれば上記の見た目パラメータを返す。B-3優先のため、「イン」は`bgAssetPreRollSec(asset) > 0`（＝直前の素材からB-3で流入中）なら発動せず、「アウト」は隣接する次素材との間に`transitionOut`が設定されていれば発動しない。
  - プレビュー: `applyBgOpacityForAsset()`/`applyBgTransformForAsset()`（プライマリレイヤーのみ。B-3のセカンダリ/トランジションプレビュー層は定義上常にB-3が優先されるため対象外）が、既存の不透明度・`background-size`/`position`に加えて`primaryBg`に`filter:blur()`/`transform:scale()`を上乗せする。この2関数は元々アクティブ化時・設定変更時にしか呼ばれていなかったため、毎フレーム滑らかにアニメーションするよう`bgVideoFadeLoop()`（既存の動画ループフェード用rAFループ）からも毎フレーム呼ぶように変更。色オーバーレイ（フェード暗転/明転）は`updateActiveBgAsset()`内で、B-3が使っていない時のみ`previewBgFadeColor`要素を使って適用（B-3側の判定も`BG_FX_OVERLAY_COLOR`テーブル参照に統一し、重複していた`===`判定を解消）。
  - 書き出し: `drawBgSourceInto()`に`fx`引数を追加し、`ctx.globalAlpha`へのぼかし・不透明度の乗算、`ctx.filter`によるぼかし、描画矩形を中心基準で拡大するズーム処理を実装。`drawCanvasBackground()`は主レイヤーの`fx`をB-3の`transState`が無い時のみ計算し、色オーバーレイも同じ`BG_FX_OVERLAY_COLOR`テーブルを参照する形に統一。
  - UI: `buildBgAssetRowBody()`の位置/ズーム設定の直後（画像・動画共通）に「登場アニメーション（イン）」「イン時間(秒)」「退場アニメーション（アウト）」「アウト時間(秒)」の4コントロールを追加。
  - **検証**: Playwrightで、fadeBlackを設定した画像素材の開始直後（進捗0.33時点）に`previewBgFadeColor`の不透明度が理論値（0.667）と一致すること、blur/zoom設定時に`primaryBg`の`filter`/`transform`が理論値（`blur(20px)`/`scale(1.15)`）と一致すること、隣接する2素材の境界でB-3（クロスフェード）と2つ目の素材のアニメーション（フェード暗転）を同時に設定した場合、境界直後（進捗0.01相当）でもフェード暗転の色オーバーレイが発動しない（＝B-3優先が機能している）こと、ズームin/outを設定した状態でも動画書き出し（`canvas`キャプチャ）がエラーなく開始できることを確認済み。コンソールエラーなし。

  - **既存タイムテーブルとの同期**: 数値入力とドラッグは共通の
    `commitLineTime()`（データ更新のみ）を通す。テーブル全体の再構築
    （`renderTable()`）はドラッグ中は一切呼ばず、対象ブロック/入力欄のみを
    直接パッチする（`refreshWaveBlock()`/`refreshTimeInputDom()`）。
    行の追加/削除・歌詞読込・プロジェクト切替などの構造変更時のみ
    `renderTable()`末尾から`renderTimelineTrack()`（トラック全体再構築）を呼ぶ。
  - **見つけて直したバグ**: 数値入力の`commit()`から律儀に毎回
    `renderTimelineTrack()`（トラック全体再構築）を呼ぶ実装にしたところ、
    「数値入力にフォーカスが残ったまま波形のハンドルをmousedownする」
    （＝ブラウザがblur→ネイティブ`change`を発火させる）だけでハンドルの
    DOM要素が再生成され、`pointerCapture`ごとドラッグが即座に中断される
    不具合があった。`refreshWaveBlock()`にブロックの存在有無で
    「既存なら直接パッチ／未存在なら`renderTimelineTrack()`にフォールバック」
    という分岐を持たせて解消（Playwrightでの自動化テストで再現・検証済み）。
  - Playwrightで「数値入力→波形ブロック反映」「ハンドルドラッグ→数値入力へ
    反映」「背景クリックでシーク」「ズーム切替」「リロード後のズーム値・
    プロジェクト（行の時間）復元」を確認済み。

    表示されない不具合を修正。原因は`#waveCanvas`/`#wavePlayhead`を
    `overflow-x:auto`を持つ`#waveScrollArea`自身の直接の子として
    `position:absolute`配置していたこと。絶対配置要素でも、containing
    blockがスクロールするその要素自身であれば一緒にスクロールしてしまう
    （position:fixed/stickyとは異なる）ため、少しスクロールしただけで
    canvas自体が画面外に流れて空白になっていた。`#waveViewport`という
    スクロールしないラッパーを新設し、`#waveScrollArea`（トラックのみ）と
    canvas/playheadを同じ`#waveViewport`の子として並列に配置することで
    解消（座標計算用の`#waveScrollArea`の矩形・`scrollLeft`はそのまま
    使えるためJS側の変更は不要だった）。Playwrightでスクロール位置ごとに
    canvasの描画有無をピクセル単位でサンプリングして再発防止を検証済み。

### C-6. 波形ブロックをドラッグ操作で（開始・終了を保ったまま）まとめて移動できるようにする

- **ステータス**: 完了
- **優先度**: 高（ユーザーが今すぐ着手を希望）
- **規模感**: 小〜中（C-1のブロック端ドラッグ（`attachHandleDrag`）と同じ
  仕組みをブロック本体のドラッグに拡張）
- **概要**: 波形ビューの歌詞ブロックの端（開始/終了ハンドル）だけでなく、
  ブロック本体をドラッグすることで、長さ（開始〜終了の間隔）を保ったまま
  行全体を時間軸上で平行移動できるようにする。ドラッグは0.01秒単位で
  スナップする（C-1のハンドルドラッグと同じ精度に統一、旧: 0.1秒）。
- **背景**: C-1のハンドルドラッグは開始・終了を個別に調整するものだが、
  行の長さは変えずに位置だけをずらしたい場面（例: 手動タイミングが
  全体的に少し早い/遅い）でも、これまではハンドルを2回ドラッグするか
  数値入力が必要だった。
- **依存関係**: C-1が前提。C-3（複数選択して一括シフト）とは別の操作系統
  （C-3はチェックボックス選択＋数値/ステッパーによる一括シフト、本項目は
  単一行をドラッグで直感的に動かす操作）だが、両方あると補完関係になる。
- **実装メモ**: ブロック端のハンドル（`attachHandleDrag`）とは別に、
  ブロック本体に`attachBlockMoveDrag(blockEl, line)`をアタッチ。ハンドルの
  `pointerdown`は`stopPropagation()`しているため、ハンドル上で始まった
  ドラッグはブロック本体側には伝播しない。ドラッグ量（秒）をそのまま
  `start`・`end`の両方に加算することで長さを保ち、`start`が0未満に
  なる場合は移動量そのものをクランプ（`start`だけでなく`end`も同じ量だけ
  クランプされるため、長さは常に厳密に保たれる）。Playwrightで
  「本体ドラッグでの平行移動」「0秒方向へのクランプ時も長さが保たれる」
  「ハンドルドラッグ（リサイズ）が本体ドラッグ追加後も引き続き正しく動く」
  ことを確認済み。

    位置に描画されることを確認済み。
  - **不具合修正（ユーザー報告）**: 「音源ファイルのトリミング（開始側）が機能していない」との指摘。
    - **原因**: `startRecording()`冒頭のデバッグ用`console.log`（動画出力の問題調査用に一時的に追加されたもの）が、`bgSizeModeSelect`/`bgZoomInput`/`bgPosXInput`/`bgPosYInput`/`previewBgImageEl`という単一背景時代のグローバル変数を参照していた。これらはB-1・B-2（複数背景素材のタイムライン配置対応）で背景の状態管理が`bgAssets[].settings`ベースに置き換わった際に削除済みで、参照するとその場で`ReferenceError`が発生し`startRecording()`全体が即座に中断していた。クラッシュ地点は`audioEl.currentTime = audioTrimStart`（トリム開始位置へのシーク）より前だったため、開始側トリムだけでなく終了側トリム・フェードも含め、書き出し機能自体が全く動作していなかった（「保存」ボタンを押しても録画中の表示にすら切り替わらない）。ユーザーが開始側トリムの不具合として気づいたのは、書き出し結果ファイルの先頭を確認していたためと推測される。

    - **検証**: Playwrightで実際に「動画として保存」ボタンをクリックし、修正前は`ReferenceError`でボタンの表示が一切変化しなかったのに対し、修正後はボタンラベルが「録画を停止」に変わり録画が正常に開始されること、コンソールエラーが出ないことを確認。トリム自体のロジック（`audioEl.currentTime = audioTrimStart`）は、このクラッシュを一時的に迂回した状態で検証しており、`audioTrimStart=3`（秒）を設定した8秒のテスト音源（無音3秒+トーン5秒）で録画を開始したところ、録音内容が冒頭の無音を含まずトーンから直接始まることをRMS振幅解析で確認済み——クラッシュ自体がロジックとは無関係な独立した不具合だったことも合わせて確認できた。

    - **対策**: この`play`イベントリスナーの直接`.play()`呼び出しを`playBgVideoElOnceSeekSettles()`経由に統一。
    - **検証**: 修正後もPlaywrightで既存の回帰テスト（トリム・フェードの検証一式）を再実行し、問題なく動作すること、コンソールエラーが出ないことを確認。トリム範囲・フェードについては実機での再現ができなかったため、修正後の状態でユーザーに再確認をお願いしている。

### E-2. 音源の始まりと終わりの音量をフェード調整できるようにする

- **ステータス**: 完了
- **優先度**: 中（暫定、要確認）
- **規模感**: 中
- **概要**: 音源の開始位置からのフェードイン、終了位置までのフェードアウトを
  それぞれ秒数指定できるようにする。
- **依存関係**: E-1（トリミング）と組み合わせて使うことが多いと想定される
  （トリムした範囲の頭とお尻を滑らかにする）が、独立して実装・利用も可能。
  `B-3`（背景動画ループ時のクロスフェード等）とは別軸（背景の視覚エフェクト
  ではなく音源の音量そのもの）。
- **決定事項**（ユーザーに確認済み）: プレビュー再生には適用せず書き出しの
  みに反映（E-1と同じ方針）。UIは波形ビュー上にフェード形状を視覚的に
  表示（ドラッグでの調整ではなく、秒数の数値入力＋視覚プレビューという
  組み合わせを採用 — フェード専用のドラッグ操作を新設するよりも実装が
  軽く、既存のトリムハンドルの視覚情報と並べて確認できるため）。
- **実装メモ**: `ensureAudioGraph()`に`exportGainNode`（`GainNode`、
  `sourceNode → exportGainNode → analyserNode → destination`の順で接続）
  を追加。通常時は`gain.value=1`のまま（録音用の`analyserNode`は
  ライブEQ表示・通常プレビューの両方と共有されているため、録画中以外は
  一切減衰させない）。`startRecording()`内でのみ、トリム後の録画区間
  （`audioTrimStart`〜`audioTrimEnd`）を基準に`linearRampToValueAtTime`
  でフェードイン/アウトを予約し、`stopRecording()`で
  `cancelScheduledValues()`＋`gain=1`にリセットして、録画直後の通常再生に
  影響が残らないようにしている。フェードイン・アウトの秒数がトリム区間長を
  超えて重なる場合は、フェードアウト側の`setValueAtTime(1,...)`アンカーを
  スキップし、フェードインのカーブから滑らかに接続されるようにした
  （そうしないと重なった瞬間に音量が1へ不自然に跳ね上がる）。
  波形ビュー上は`#waveFadeInOverlay`/`#waveFadeOutOverlay`
  （`linear-gradient`によるフェード形状の視覚表示、非インタラクティブ）を
  `#waveFadeInInput`/`#waveFadeOutInput`（秒数入力）と連動させ、
  `redrawTrimFadeOverlay()`が同時に位置・幅を更新する。Playwrightで
  トリムハンドルのドラッグ・フェード秒数入力・リロード後の永続化・
  新規音源読込時のリセット・録画開始時に`audioEl.currentTime`がトリム
  開始位置にスナップすることを確認済み。

    - 検証: 実尺が異なる3本のテスト動画（約3.8秒・1.3秒・2.3秒、`MediaRecorder`で生成）を一括追加し、全3本の配置区間の長さが実尺と一致し、かつ隣接する素材間に隙間も重なりもないことをPlaywrightで確認。コンソールエラーなし。

* **【対応済み】** モバイルで「SRTを開く」からSRTファイルを選択できない不具合を修正。同時に、歌詞タイムテーブルの「全行クリア」機能を追加。
  - **不具合修正**: `#srtInput`の`accept`属性が`.srt,text/plain,application/x-subrip`だった。`.srt`は拡張子・MIMEタイプともにOS標準の対応表に載っていないマイナー形式のため、他アプリ経由で受け取ったファイルはiOS/Androidどちらのファイルピッカーでも`application/octet-stream`等の汎用タイプとして扱われがちで、指定したMIMEタイプに一致せずグレーアウト・非表示になっていたと判断（`accept="audio/*"`のみだった`#audioInput`で以前に見つかった不具合と同系統だが、こちらは拡張子を指定していても起きる、より根の深いケース）。`text/*`をワイルドカードとして追加（`.srt,text/plain,application/x-subrip,text/*`）し、MIMEタイプが多少ずれていても拡張子・大まかなカテゴリのどちらかで拾えるようにした。
  - **新機能**: 歌詞タイムテーブルのツールバーに「全行クリア」ボタンを追加（`.ghost-btn.danger`、ホバー時に赤く表示）。既存の削除確認（背景素材の全クリア・プロジェクト削除）はいずれも`window.confirm()`のワンクリック確認だったが、全行クリアは元に戻す手段が一切ない（このアプリにundo/履歴機構が存在しない）操作であるため、より厳格に`window.prompt()`で「削除」という文字列の入力を要求し、一致しない限り実行しないようにした。クリックしても行が0件の場合は何もしない（ダイアログも出さない）。
  - **検証**: Playwrightで、ダイアログをキャンセルした場合・「削除」以外の文字列を入力した場合はいずれも行数が変化せずエラーステータスが表示されること、「削除」と正しく入力した場合は全行が消え成功ステータスが表示されること、行が0件の状態でクリックしてもダイアログ自体が出ないことを確認。あわせて`#srtInput`の`accept`属性が意図通り更新されていることも確認。コンソールエラーなし。
